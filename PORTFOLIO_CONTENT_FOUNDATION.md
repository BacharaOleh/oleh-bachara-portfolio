# Portfolio content foundation

This document is the editorial source for the portfolio redesign. It deliberately avoids claims that cannot be demonstrated in a case study, anonymous testimonials, simulated “live” systems, and inflated seniority labels.

## 1. Positioning

**PL** — Web Developer — platformy produktowe i rozwój techniczny

**EN**

**PL**

### What the portfolio should communicate

- You are a practical web developer, not a generic “systems architect”.
- You understand commercial websites: content, catalogue UX, speed, analytics and operational reliability.
- You can explain your contribution and its business effect clearly.
- You have a focused body of work, rather than a long list of technologies.

### Claims policy

Only publish a result when it can be explained in an interview or backed by a screenshot, report, before/after capture, repository, client permission, or a clear description of the measurement period. Prefer “improved mobile PageSpeed from approximately 45 to 90+ in the tested pages” over universal claims such as “zero downtime” or “100% uptime”.

## 2. Site map

```
/                         Home / selected work
/work/reh4mat            Main commercial case study
/work/platform-migration Infrastructure & performance case study
/work/telegram-auth      Technical integration case study
/about                   Optional short biography and CV
```

Do not create a separate deployed website for every case. Each case should be a focused page in this portfolio, with its own visual rhythm and evidence. A separate site is justified only when the work itself is a real independent product or a complete branded redesign that can be publicly shown.

## 3. Home page — final information architecture

1. **Navigation** — Work, About, Contact. Language selector only if Polish and English are both complete.
2. **Hero** — one sentence about the work, two actions: View selected work / Contact.
3. **Selected work** — exactly three project cards. One outcome, one sentence, one image per card.
4. **Capabilities** — three compact areas: Product platforms; Performance & migration; Measurement & technical growth.
5. **About** — experience, education, languages in one restrained block.
6. **Contact** — email, LinkedIn, CV. One clear invitation to get in touch.

Remove the perspective switch, recruiter modal, command palette, floating live-status badge, project configurator, simulated monitors, architecture simulator and anonymous review cards. They add interaction but not evidence.

## 5. Case-study template

Every case should use the same factual framework, but have an individual art direction and set of assets.

1. **Title and one-line outcome**
2. **Context** — client/domain, audience, timeframe and what existed before
3. **My role** — what you personally owned; separate team work from yours
4. **Problem** — no more than three concrete constraints
5. **Approach** — decisions and implementation, supported by diagrams or captures
6. **Result** — baseline, measurement source, period and limitation
7. **Evidence** — before/after screenshots, GA4/GSC extracts with sensitive data hidden, code or technical artefacts where public
8. **What I learned** — an honest short conclusion

### Reh4mat — product catalogue ecosystem

**EN — summary**  
From 2023 to 2026, I supported the web presence of Reh4mat across a group of corporate sites and product catalogues serving PL, UA and EU markets. My work combined WordPress/PHP development, catalogue presentation, technical SEO and analytics.

**EN — challenge**  
The sites had to present a broad product range clearly while carrying legacy technical constraints. Content structure, asset weight, page speed and measurement all affected how effectively the catalogue supported users and search visibility.

**EN — role & approach**  
I worked on catalogue and product-page improvements, asset optimisation, technical cleanup, structured data and GA4 conversion measurement. I also supported experiments around calls to action and email journeys. The work was iterative: diagnose a bottleneck, implement a focused improvement, then measure the effect.

**EN — result**  
During the reported measurement period, the main site recorded +40% organic traffic growth. Email campaigns achieved 30–36% engagement according to the campaign metric used internally. The case page should show the exact period, data source and selected screenshots before publication.

**PL — summary**  
W latach 2023–2026 wspierałem obecność webową Reh4mat w grupie serwisów korporacyjnych i katalogów produktów dla rynków PL, UA i UE. Moja praca łączyła rozwój WordPress/PHP, prezentację katalogów, techniczne SEO i analitykę.

**PL — challenge**  
Serwisy musiały jasno prezentować szeroką ofertę produktów, jednocześnie działając w warunkach zastanej architektury. Struktura treści, waga zasobów, szybkość stron i pomiar wpływały na użyteczność katalogu oraz widoczność w wyszukiwarce.

**PL — role & approach**  
Pracowałem nad katalogiem i stronami produktów, optymalizacją zasobów, porządkowaniem elementów technicznych, danymi strukturalnymi oraz pomiarem konwersji w GA4. Wspierałem również testowanie CTA i ścieżek e-mail. Działaliśmy iteracyjnie: diagnoza problemu, konkretna poprawa, pomiar efektu.

**PL — result**  
W opisywanym okresie główna strona odnotowała +40% wzrostu ruchu organicznego. Kampanie e-mail osiągały 30–36% zaangażowania według stosowanej wewnętrznie metryki. Przed publikacją case study należy dodać dokładny okres, źródło danych i wybrane zrzuty ekranu.

### Platform migration & performance recovery

**EN — summary**  
This work focused on moving web platforms to a stronger hosting setup while reducing performance bottlenecks that affected mobile users.

**EN — challenge**  
The migration had to protect existing sites, domains and database content while avoiding disruption to visitors. At the same time, slow pages and heavy assets required focused technical improvement.

**EN — role & approach**  
I prepared migration steps, supported DNS and SSL configuration, checked database and asset delivery, and worked on image optimisation, lazy loading and page-weight reduction. Performance checks were used to prioritise the pages with the clearest user impact.

**EN — result**  
For selected mobile pages, PageSpeed results improved from approximately 45 to 90+. Do not claim universal zero downtime unless logs and monitoring evidence can support it. Instead, describe the migration window and observed service continuity precisely.

**PL — summary**  
Projekt dotyczył przeniesienia platform webowych do lepszego środowiska hostingowego oraz ograniczenia problemów z wydajnością odczuwalnych szczególnie przez użytkowników mobilnych.

**PL — challenge**  
Migracja musiała zabezpieczyć istniejące strony, domeny i dane w bazach, a jednocześnie ograniczyć ryzyko zakłóceń dla użytkowników. Równolegle wolne strony i ciężkie zasoby wymagały konkretnych usprawnień technicznych.

**PL — role & approach**  
Przygotowałem etapy migracji, wspierałem konfigurację DNS i SSL, sprawdzałem bazę danych oraz dostarczanie zasobów. Pracowałem nad optymalizacją obrazów, lazy loadingiem i zmniejszeniem wagi stron. Priorytety ustalałem na podstawie kontroli wydajności stron o największym znaczeniu dla użytkownika.

**PL — result**  
Na wybranych stronach mobilnych wyniki PageSpeed wzrosły z około 45 do 90+. Nie należy deklarować całkowitego braku przestojów bez potwierdzenia w logach i monitoringu; lepiej dokładnie opisać okno migracji i zaobserwowaną ciągłość działania.

### Telegram authentication integration

**EN — summary**  
A technical project exploring how a Telegram-based sign-in flow can be connected safely to a web application and database workflow.

**EN — challenge**  
The integration needed to connect an external identity flow with the application while keeping payload validation, session handling and data synchronization explicit and maintainable.

**EN — role & approach**  
I implemented the PHP-side integration, worked with signed authentication data, webhook requests and application/database synchronization. The final public case should include a simplified architecture diagram and a redacted code excerpt, not a public live-login demo.

**EN — result**  
Use this case to demonstrate implementation thinking rather than unsupported operational metrics. Include active users, latency or uptime only when their source and measurement period can be shown.

**PL — summary**  
Projekt techniczny pokazujący, jak połączyć logowanie oparte na Telegramie z aplikacją webową i przepływem danych w bazie.

**PL — challenge**  
Integracja musiała połączyć zewnętrzny proces tożsamości z aplikacją, zachowując jasną walidację danych, obsługę sesji i synchronizację danych.

**PL — role & approach**  
Zaimplementowałem integrację po stronie PHP, pracowałem z podpisanymi danymi uwierzytelniającymi, żądaniami webhook i synchronizacją aplikacji z bazą. Publiczny case powinien zawierać uproszczony diagram architektury oraz zanonimizowany fragment kodu, a nie publiczne demo logowania.

**PL — result**  
Ten case ma pokazywać sposób myślenia i implementację, a nie niepotwierdzone metryki operacyjne. Liczbę użytkowników, opóźnienie lub uptime dodaj wyłącznie wtedy, gdy można wskazać źródło i okres pomiaru.
